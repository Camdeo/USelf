# USelf Test v0.1 — пошаговый запуск через GitHub + Render

Эта инструкция рассчитана на человека, который не хочет разбираться в DevOps. Цель: получить публичную HTTPS-ссылку на тест и отправить приватную ссылку второму участнику.

## Что уже подготовлено

В репозитории есть:

- `render.yaml` — Render читает этот файл и сам создаёт инфраструктуру;
- `Dockerfile` — собирает React и запускает FastAPI одним веб-сервисом;
- `backend/` — API, приватные токены, ответы, подсчёт мэтчей;
- `frontend/` — интерфейс теста;
- `backend/data/questions.demo.json` — временный демонстрационный набор вопросов;
- PostgreSQL подключается автоматически через `render.yaml`;
- HTTPS и публичный адрес вида `https://uself-test-....onrender.com` выдаёт Render.

Для первого тестового запуска **не нужно** вручную создавать базу, копировать `DATABASE_URL`, покупать домен или настраивать SSL.

# Часть 1. Загрузить проект на GitHub

## Вариант A — через сайт GitHub, без терминала

1. Скачай архив `uself-test-render-ready.zip` и распакуй его на компьютере.
2. Открой GitHub и войди в аккаунт.
3. Нажми `+` в правом верхнем углу → `New repository`.
4. В поле **Repository name** напиши, например: `uself-test`.
5. Репозиторий можно оставить **Private**. Render умеет работать с приватным GitHub-репозиторием после выдачи доступа.
6. **Не добавляй** README, `.gitignore` или License через GitHub — всё нужное уже лежит в архиве.
7. Нажми `Create repository`.
8. На странице пустого репозитория нажми ссылку `uploading an existing file` или `Add file` → `Upload files`.
9. Перетащи **содержимое распакованной папки** `uself-test-render-ready` в окно загрузки. В корне репозитория должны оказаться непосредственно:
   - `render.yaml`
   - `Dockerfile`
   - `README.md`
   - папка `backend`
   - папка `frontend`
10. Внизу страницы в поле commit message можно оставить `Initial USelf test`.
11. Нажми `Commit changes`.

### Очень важная проверка GitHub

После загрузки открой главную страницу репозитория. Ты должен видеть `render.yaml` **сразу в корне** репозитория, а не внутри дополнительной папки вроде `uself-test-render-ready/uself-test-render-ready/render.yaml`.

Если `render.yaml` лежит в корне — всё правильно.

# Часть 2. Подключить GitHub к Render

1. Открой https://dashboard.render.com/ и войди / зарегистрируйся.
2. Если Render ещё не подключён к GitHub, он предложит подключить GitHub account. Разреши Render доступ к репозиторию `uself-test`.
   - Для приватного репозитория можно дать доступ только к выбранному репозиторию.
3. В Render Dashboard нажми `New` → `Blueprint`.
4. В списке репозиториев найди `uself-test` и нажми `Connect`.
5. Render автоматически найдёт файл `render.yaml` в корне.
6. Blueprint можно назвать, например, `uself-test`.
7. Branch оставь `main`, если GitHub создал ветку `main`.
8. Render покажет ресурсы, которые собирается создать:
   - Web Service: `uself-test`
   - PostgreSQL: `uself-test-db`
9. Убедись, что оба имеют план **Free**.
10. Нажми `Deploy Blueprint` / `Apply` (название кнопки в интерфейсе может немного отличаться).

После этого Render сам:

- создаст PostgreSQL;
- передаст приложению строку подключения к базе;
- соберёт Docker image;
- внутри Docker соберёт React;
- запустит FastAPI;
- выдаст HTTPS-адрес.

Никакие секреты в этом прототипе вручную вводить не требуется.

# Часть 3. Понять, что деплой завершился

На странице Blueprint / Web Service будут идти логи сборки.

Нормальный финал выглядит примерно так:

- Build: successful
- Deploy: live
- Web service получил адрес `https://....onrender.com`

Открой адрес Web Service.

Ты должен увидеть стартовую страницу USelf с кнопкой **«Создать совместный тест»**.

## Быстрая техническая проверка

Добавь `/health` к адресу сайта, например:

`https://твой-сайт.onrender.com/health`

Должен появиться ответ:

```json
{"ok": true}
```

Если `/health` работает, backend запущен.

# Часть 4. Проверить весь сценарий до отправки девушке

Сначала рекомендую сделать пробную комнату самому.

1. Открой главную страницу.
2. Введи два имени/псевдонима.
3. Нажми **«Создать совместный тест»**.
4. Появятся две разные ссылки:
   - твоя приватная ссылка;
   - ссылка второго участника.
5. Открой свою ссылку в обычном окне браузера.
6. Вторую ссылку открой в **другом браузере, приватном окне или на другом телефоне**.
7. Ответь на все демонстрационные вопросы с обеих сторон.
8. На каждой стороне нажми **«Завершить и ждать совпадения»**.
9. После завершения обоих открой результаты.
10. Проверь главное правило:
    - `Да + Да` показывается;
    - `Да + Возможно` показывается;
    - `Возможно + Возможно` показывается;
    - если хотя бы один ответил `Нет`, вопрос в результатах отсутствует.

**Не пересылай свою приватную ссылку партнёру.** Токен в ссылке является доступом именно к ответам конкретного участника.

# Часть 5. Как использовать после проверки

Когда тест работает:

1. Создай новую комнату специально для реального прохождения.
2. Скопируй **только ссылку партнёра** и отправь её девушке.
3. Свою ссылку сохрани себе.
4. Каждый проходит тест независимо.
5. После того как оба завершили прохождение, каждый может открыть экран совпадений.

Сырые ответы второго участника API не показывает. В результат попадают только вопросы, где оба выбрали `Да` или `Возможно`.

# Часть 6. Что важно знать про бесплатный Render

На момент подготовки этой инструкции Render официально указывает следующие ограничения Free:

- бесплатный Web Service засыпает после 15 минут без входящих запросов;
- первый запрос после сна может открываться заметно дольше обычного — это нормально;
- на workspace даётся 750 бесплатных instance-hours в месяц;
- бесплатная PostgreSQL имеет лимит 1 GB;
- бесплатная PostgreSQL **истекает через 30 дней после создания**;
- у одного workspace одновременно может быть только одна бесплатная PostgreSQL;
- у бесплатной PostgreSQL нет бэкапов.

Для нашего теста на этой неделе это подходит. Для постоянного USelf эту схему потом нужно будет заменить/апгрейдить.

## Если Render пишет, что нельзя создать Free PostgreSQL

Скорее всего, в твоём Render workspace уже существует другая бесплатная база. Render разрешает только одну Free PostgreSQL на workspace.

Варианты:

- удалить старую ненужную Free DB и повторить Blueprint Sync;
- использовать существующую БД, но тогда потребуется ручная настройка;
- временно выбрать платный план — для текущего теста это обычно не требуется.

# Часть 7. Если что-то не работает

## Сайт не открывается сразу

Если Free Web Service спал, первый запрос может быть медленным. Обнови страницу после запуска сервиса.

## `502` или `Application failed to respond`

Открой Render → `uself-test` → `Logs` и посмотри последние красные строки. Чаще всего проблема будет видна там.

## Ошибка подключения к PostgreSQL

Если проект был создан через Blueprint из приложенного `render.yaml`, `DATABASE_URL` должен подставиться автоматически. Проверь Render → Web Service → Environment: переменная `DATABASE_URL` должна существовать.

## Главная страница работает, но создание комнаты падает

Открой `/health`. Если он работает, затем посмотри `Logs` в момент нажатия «Создать совместный тест». Это позволит отличить ошибку базы от ошибки интерфейса.

## После изменения кода сайт не обновился

При push/commit в ветку `main` Render по умолчанию запускает новый deploy. Его статус виден во вкладке Deploys. При необходимости можно выбрать `Manual Deploy` → `Deploy latest commit`.

# Часть 8. Как потом заменить демонстрационные вопросы на настоящий банк USelf

Сейчас файл:

`backend/data/questions.demo.json`

содержит небольшой тестовый набор. Он нужен только для проверки механики и Render.

Перед реальным полноценным прохождением мы заменим его данными из канонического банка `USelf_Итоговый_банк_вопросов_v1.xlsx`.

Важно: функция seed сейчас заполняет таблицу `questions` только если она пустая. Поэтому после замены банка в уже существующем Render Postgres старые демо-вопросы сами не исчезнут.

Для первого полноценного запуска есть два безопасных пути:

- создать новую чистую БД;
- либо добавить миграцию/команду обновления банка вопросов.

Я рекомендую второй вариант, когда подключим финальные 312 вопросов — так мы не будем вручную удалять базу при каждой правке.

# Что считать успешным результатом этого этапа

Этап завершён, если:

- GitHub содержит проект и `render.yaml` в корне;
- Blueprint Render зелёный;
- `/health` возвращает `{"ok": true}`;
- главная страница открывается по HTTPS;
- создаются две разные приватные ссылки;
- оба участника могут независимо сохранить ответы;
- после submit обоих показываются только взаимные `Да/Возможно`;
- вопрос с `Нет` хотя бы с одной стороны не появляется в результатах.

После этого инфраструктура готова, и можно подключать полный русский банк вопросов и уже проводить настоящее прохождение.
